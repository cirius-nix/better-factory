# task-site-lib: The site library, the site assets, and the derived feature order

**Plan:** [Implementation plan](README.md)
**Covers:** req-browsable-docs, spec-site-render
**Context:** context-factory
**Component:** services/factory
**Aggregate:** agg-repository-blueprint
**Depends on:** [task-delivery-facade](task-delivery-facade.md).
**can-parallel:** No. The task touches the component `services/factory`, the context
`context-factory`, and the aggregate `agg-repository-blueprint`. Tasks that share a component,
a context, or an aggregate run in sequence.

## Goal

Ship the site asset tree, render the site project and the file `site.json` with the derived
feature order, and join the site files to the file plan as rendered files.

## Steps

1. Create the asset tree `assets/delivery/site/` with the content sources of the emitted-files
   table of spec-site-render: `package.json`, `package-lock.json`, `docusaurus.config.js`,
   `sidebars.js`, `.gitignore`, `src/css/custom.css`, and `README.md`. The file `site.json` is
   not an asset; the module renders it.
2. Pin the packages of `package.json` at one exact version and commit `package-lock.json`. The
   factory owns both files. The copy mode `managed` fails the drift check on a hand edit
   (C-36).
3. Write `docusaurus.config.js` with the rules of spec-site-render point 4: the file reads
   `./site.json` for `title`, `url`, `baseUrl`, `staticDirectories`, and `featureOrder`; the
   docs path is `../../docs`; the docs route is `/`; the sidebar path is `./sidebars.js`;
   number-prefix parsing is off; the exclude list holds the Docusaurus defaults and
   `**/templates/**`; a folder without an index gets a generated index page;
   `trailingSlash = true`; both broken-link settings are `warn`; the markdown format is
   `detect`; the classic preset disables the blog; the classic theme reads
   `./src/css/custom.css`; the navbar title is `site.title`.
4. Write the one comparator of the sidebar in `docusaurus.config.js` with the priority order of
   spec-site-render point 7: the feature position in `featureOrder`, then `index` or `README`
   first, then the phase rank `requirements`, `specifications`, `decisions`, `tasks`, then the
   semantic version order below `versions`, then `change-initial` first below `changes`, then
   the case-insensitive label compare. The comparator applies each special rule only to its
   item type and parent folder. Mark each rule in the file with its required text, for example
   the read `site.featureOrder`, the names `index` and `README`, the four phase names, the name
   `change-initial`, and a case-insensitive compare (for example `toLowerCase`). The check
   reads this text and runs no JavaScript (C-23).
5. Write `sidebars.js` with the autogenerated sidebar of the docs tree. Write `.gitignore`
   with the build output of the site. Write `src/css/custom.css` with the site style. Write
   `README.md` with the guide of the site project. The files `custom.css` and `README.md` use
   the copy mode `seed` (C-36). The `README.md` states the manual steps of the
   azure-static-web-app target and the Pages source setting (spec-publish).
6. Create `lib/site.nix`. The library holds the emitted-files table, the function `featureOrder`
   with the argument `repoRoot`, and the function `siteFiles` with the arguments `settings` and
   `repoRoot`. `siteFiles` returns the `extraFiles` entries and the rendered-source list of the
   run (C-32).
7. Derive the feature order from the feature index of the repository under generation
   (C-22, adr-derived-feature-order). Read `repoRoot + "/docs/artifact/README.md"`. Take the
   rows of the `## Features` table in order and extract the `feat-<name>` folder basename of
   each row. List the feature folders below `repoRoot + "/docs/artifact/"`. A listed folder
   keeps the row order. An unlisted folder follows the listed folders in alphabetical order.
   An absent index, an absent table, or an empty table gives no listed row, so the order is
   the alphabetical order of the feature folders. The factory holds no feature-order option
   and no hand list of feature names.
8. Render the site files. When `settings.site.enable` is true, read each asset file of the
   table into a store path with `builtins.toFile` and render `site.json` with
   `builtins.toJSON`. Each file joins the plan as an `extraFiles` entry with the copy mode of
   the table. Each `source` is a store path of the run. The same store paths join the
   rendered-source list of the run. A direct path under `assets/delivery/` is not the `source`
   of a plan entry (C-21, C-33). When `enable` is false, the plan holds no site file.
9. Add the delivery file computation to `modules/delivery.nix`: the function `deliveryFiles`
   with the arguments `settings` and `repoRoot` returns the `extraFiles` entries and the
   rendered-source list of the run. This task joins the site files. The later tasks join the
   CI file and the notifier file.
10. Add the fixture trees `assets/delivery/fixtures/index/` and
    `assets/delivery/fixtures/no-index/`. Each tree holds a `docs/artifact/` folder. The first
    tree holds an index with a `## Features` table and three feature folders. The second tree
    holds no index and two feature folders. Each feature folder holds a file, so the folder
    exists in the repository.
11. Advance `modules/seed-check.nix`: the plan takes the delivery `extraFiles` and the rendered
    sources of the run. Add the site check fixtures of spec-site-render: one fixture with
    `enable = true`, one fixture with `enable = false`, one fixture index, and one fixture
    without an index.

## Checks

- Build the plan of the `enable = false` fixture. It holds no site file of the emitted-files
  table.
- Build the plan of the `enable = true` fixture. It holds each file of the table with its
  content source and its copy mode.
- Build the plan of a fixture with an `extraFiles` entry whose source is a direct path under
  `assets/delivery/site/`. The file-plan check rejects it.
- Read the rendered `site.json` of the `enable = true` fixture with `builtins.fromJSON`. The
  value equals the fixture settings and the derived order.
- Call `siteFiles` with the root of the fixture index. The derived order equals the row order
  of that fixture index.
- Call `siteFiles` with the root of the fixture without a row for one folder. That folder
  follows the listed folders in alphabetical order.
- Call `siteFiles` with the root of the fixture without an index. The order is the alphabetical
  order of the two feature folders.
- Read `docusaurus.config.js`. It holds the read of `site.featureOrder` and a marker of each
  comparator rule.
- Run the seed check. It runs no `npm` command and no JavaScript file. The comparator proof
  reads the required text of the config asset only (C-23).
- Search `lib/site.nix` and `modules/delivery.nix` for the names `feat-foundation`,
  `feat-orchestration`, `feat-design`, and `feat-delivery`. No match appears.
- Run the copy step on a fixture plan that holds `apps/documentation/src/css/custom.css` with
  the copy mode `seed`. Edit the file and run the copy step again. The bytes stay.
- Run the seed check of both archs. Both are green with exactly five result lines.

## Done criteria

- The asset tree holds the seven content sources of the emitted-files table (C-36).
- The site files join the plan as `extraFiles` entries with rendered sources, and no plan entry
  has a direct source under `assets/delivery/` (C-21, C-33).
- The feature order derives from the feature index of the repository under generation
  (C-22, C-32).
- The config asset holds the comparator rules and their markers (C-23).
- The site check fixtures pass for the enabled and the disabled site.
